# GitLab CI — интеграция frontend

Изменения выполнены локально на `feat/frontend-dashboard`. Существующие изменения удаления Mock-режима и страницы сравнения сохранены. Backend, `.env.local`, production-инфраструктура и CI/CD не менялись. Коммиты и операции записи в GitHub не выполнялись. Реальные pipeline и Coverage Runs для проверки не запускались.

## Контракты и совместимость

Изучены актуальные `app/gitlab_api.py`, `app/gitlab_client.py`, `app/gitlab_runs.py` и [docs/gitlab-e2e.md](https://github.com/QualiMeter/GraphQL-Coverage-Proxy-Beckend/blob/main/docs/gitlab-e2e.md) в backend-репозитории. Контракты сверены с [production OpenAPI](https://graphql.rebyte.fun/openapi.json) 18 ноября 2026 года.

В production есть все три требуемых маршрута: ветки, запуск и статус. `LaunchInput` и обязательные поля `PipelineOut` совпадают. В репозитории дополнительно есть необязательные projectId/branch/commitSha/environment и маршрут jobs; production OpenAPI их пока не содержит. Реализация опирается на доступный контракт, jobs не требуются заданием.

В приложенном задании последний абзац обрывается на «Не передавай GitLab API-т». Frontend не принимает, не хранит и не отправляет GitLab API-токен: он работает только с cookie-сессией и CSRF Coverage Proxy. Нет полей GitLab host/project ID и обходов серверного доступа.

## Реализованные возможности

- В существующем диалоге «Новый прогон» добавлены два способа: обычный и GitLab CI. Обычная форма, создание через `/api/runs`, показ ID и последующее ручное завершение сохранены.
- GitLab-форма показывает выбранные сервис и снимок, выбор ветки и необязательное название. Список веток запрашивается по одной странице, до 100 записей. Поиск выполняется среди загруженных веток, следующая страница — по кнопке. Ошибка загрузки отличается от пустого ответа GitLab. Смена сервиса/снимка перемонтирует форму и сбрасывает её выбор.
- Запуск выполняет единственный POST `/api/runs/gitlab` с существующими cookie/Origin/CSRF. Отдельный POST создания Coverage Run не вызывается. Кнопка и переключение режима блокируются во время отправки; синхронная защита предотвращает двойную отправку.
- При 202 сохраняется настоящий runId, обновляется история и отдельно читается фактический RunOut. Новый прогон выбирается только при сохранении сервиса, снимка и ревизии сессии. Поздний ответ из прежнего контекста не переключает рабочее пространство.
- Учитывается `runId` внутри 502 (`detail.code`/`detail.runId`) и даже в неполном успешном ответе. Такой прогон восстанавливается по ID и отслеживается; POST автоматически не повторяется.
- При `launch_unknown`, сетевой ошибке или потерянном ответе повторная отправка формы блокируется. Пользователь получает сообщение о неопределённом результате и кнопку проверки истории. Произвольный текст upstream-ошибок не выводится; безопасные коды и известные серверные причины переводятся в понятные сообщения.
- Панель выбранного прогона раздельно показывает pipelineStatus и runStatus, ID pipeline, безопасную HTTPS-ссылку, ошибки, неполный сбор, реальные обращения и покрытие. `completed` Coverage Run не интерпретируется как успешный GitLab pipeline.
- Для выбранного прогона выполняется последовательный GET статуса с интервалом 10 секунд после завершения предыдущего запроса. Параллельных запросов статуса нет. Polling прекращается по trackingFinished, а не по runStatus; неполный сбор с продолжающейся сверкой корректно отслеживается. После 401/403 автоматическое чтение приостанавливается до изменения сессии или ручного повтора.
- Покрытие и статистика обновляются существующим `refreshRunAnalytics`, без параллельного расчёта и сброса открытых подробностей на каждом тике. При окончании отслеживания выполняется финальное обновление после завершения текущих загрузок. Статус RunOut и история обновляются при переходе состояния.
- Смена прогона, сервиса, снимка, сессии и размонтирование отменяют устаревшие GET-запросы и таймер. История не опрашивает все pipeline. После выбора исторического прогона его GitLab-метаданные читаются отдельно.
- 404 статуса обычного прогона не показывается как ошибка. Для уже известного GitLab-прогона потеря метаданных не превращается в разрешение ручного завершения. До завершения проверки связи ручной `/finish` заблокирован; для GitLab-managed он не предлагается и дополнительно запрещён обработчиком.
- Поддержаны ошибки 401/403/404/409/422/502/503, не настроенная интеграция, проблемы GitLab-авторизации и сети. При 401 существующая сессия перепроверяется. Внешние ссылки проверяются, открываются с noopener/noreferrer.
- Использованы существующие стили и переменные светлой/тёмной темы; панель адаптируется в одну колонку на узком экране.

## Проверки и ограничения

- `npm run lint`: успешно.
- `npm test`: 26 файлов, 245 тестов успешно; добавлено 33 теста.
- `npm run build`: успешно. Vite по-прежнему предупреждает о JS-файле больше 500 kB.
- `git diff --check`: успешно.

Тесты проверяют единственный POST и CSRF, отсутствие лишнего create-run, launch_unknown, сетевые ошибки, сохранение runId из 502/неполного ответа, все перечисленные HTTP-статусы, конфигурацию вместо ложного пустого списка, постраничную загрузку веток, проверку URL и DTO. Fake timers проверяют интервал, отсутствие перекрывающихся GET, остановку по trackingFinished, продолжение сверки при failed/incomplete, отмену и игнорирование поздних ответов. Проверены ordinary 404, запрет ручного finish для GitLab/неизвестного состояния, независимые failed pipeline и completed Coverage Run, смена сервиса/снимка/сессии.

Браузер на реальном backend: загрузились существующий сервис, снимок, выбранный прогон и аналитика. GitLab-статус без сессии вернул 401, показано понятное сообщение. «Новый прогон» без авторизации открыл существующий диалог входа; он закрыт без отправки формы. Основной граф и сводка остаются доступны. Авторизованная operator/admin-сессия в проверочном браузере отсутствовала.

Не проверены реальный список веток с grant, авторизованная форма, запуск pipeline, рост покрытия от E2E, действующий live polling, реальные 502/409 и ручной finish обычного прогона после проверки связи. Эти пути покрыты кодом и unit-тестами, но полный браузерный и сквозной регресс не выполнен. Реальный запуск pipeline требует отдельной проверки с оператором и настроенной серверной интеграцией; он не выполнялся этой задачей.

В изученной документации backend отдельно отмечены зависимости от доверенного GitLab ref, workflow/jobs, защищённых CI variables и режима QA runner, который использует переданный Coverage UUID без самостоятельного create/finish. Наличие frontend-кнопки и маршрута не подтверждает настройку этих компонентов или сквозной сбор E2E на текущем стенде. GitLab-проект, QA и настройки сервера здесь не изменялись.
