# GitLab CI History

## История прогонов

В существующую историю добавлены основные фильтры ветки, pipeline status, Coverage Run status, сортировка и направление. Дополнительные фильтры раскрываются на месте: полный SHA, pipeline ID, environment, job ID/name/status и период запуска. Фильтры применяются по кнопке, объединяются сервером через AND и сбрасывают offset. Названия веток вводятся точно, список веток запуска pipeline не используется как каталог истории.

Подключён расширенный GET `/api/runs?serviceId=...` / `snapshotId=...`. DTO сохраняет только подтверждённый `ci`, поддерживает старые ответы без него и не извлекает данные из пользовательского metadata. X-Total-Count используется для найденного количества и пагинации.

В одной компактной колонке GitLab CI показаны ветка, короткий SHA с полным значением в tooltip, pipeline ID/status, окружение и безопасная HTTPS-ссылка. Coverage Run status остаётся отдельным. Без ci показано нейтральное «Нет данных CI», без утверждения о ручном запуске. Выбор строки и прогона сохранён.

Jobs раскрываются под строкой. Только при раскрытии вызывается GET `/api/runs/{runId}/gitlab/jobs?limit=100&offset=...`. Поддержаны страницы, обновление, ошибки/пустой результат, длительность по фактическим startedAt/finishedAt и отдельные записи повторных jobs с разными ID. jobsSyncedAt=null и jobsFinalized=false явно обозначают неполную/неокончательную синхронизацию. Это не новый мониторинг и не список E2E-тестов.

Контекстные ключи и AbortController исключают старые результаты при смене запроса/сервиса/прогона; закрытие jobs отменяет загрузку. На узких экранах строки истории переходят в компактный вертикальный вид без расширения таблицы. Исправлены старые ограничения высоты контейнера истории: фильтры, строки и пагинация доступны через прокрутку при раскрытой сводке. Изменение прокрутки ограничено страницей истории.

## Сравнение прогонов

В существующем выборе, выбранной последовательности, списке результатов и контексте baseline/target показаны те же CI-метаданные. Поиск кандидатов дополнен серверными branch/environment и всегда ограничен status=completed и одним snapshotId.

Поиск кандидатов не заменяет выбранные runIds, baseline или target. Уже выбранные прогоны остаются в отдельном существующем списке, даже если новый фильтр скрывает их среди кандидатов. Можно сравнивать разные ветки и разные pipelines одного снимка; обычные прогоны без CI также доступны. Смена snapshot сбрасывает выбор и результат. Ветка/окружение передаются при переходе из истории в сравнение.

Механизм compareRuns, вычисления покрытия/дельт и формат экспорта не менялись. Фильтры списка кандидатов не попадают в тело экспорта сравнения и не подменяют выбранные UUID. В результатах не дублируются jobs.

## Доступ и безопасность

Read-only проверены актуальные [docs/gitlab-coverage-history.md](https://github.com/QualiMeter/GraphQL-Coverage-Proxy-Beckend/blob/main/docs/gitlab-coverage-history.md), app/api_models.py, app/journal.py и app/gitlab_api.py backend.

Session не содержит полного списка service grants, поэтому наличие grant не выводится из viewer/analyst/operator. Анонимно CI-фильтры отключены; публичная история работает. Авторизованный пользователь может явно применить CI-фильтр, а backend окончательно проверяет доступ. При 401/403/404 на CI-запрос автоматически загружается обычная история с сохранением обычных фильтров статуса/периода и сортировкой по времени. В UI явно сообщается, что CI-ограничения не применены; обычная история не блокируется. По названию роли grant не объявляется.

Jobs предлагаются только при возвращённом backend подтверждённом ci и авторизованной сессии; заранее не загружаются. Отдельные запросы для проверки grant не добавлялись. Ошибки 401/403/404/422 и сети сохраняются, а не заменяются успешным пустым результатом. Для внешних ссылок повторно используется pipelineLink: HTTPS, без credentials, query/hash и управляющих пробельных частей; target=_blank, rel=noopener noreferrer. Небезопасный URL не делает обычную историю недоступной — ссылка просто не отображается.
